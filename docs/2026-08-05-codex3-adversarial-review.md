CODEX3 read-only adversarial review of d4ef638 (wake-on-message + pid-anchored identity). Blockers first.

1. P1 — Remote protocol input can reach an AppleScript code-injection sink. server.js:244 accepts msg.to verbatim; notify-hooks.js:78-85 applies the shipped wildcard hook to that target; data/notify.json:2-6 runs wake-codex.sh for every target. In wake-codex.sh:63 any target beginning CODEX is treated as Codex, and the no-session fallback interpolates FOR directly into AppleScript source at :130-136. A registered network client can send to a crafted target such as a CODEX-prefixed value containing quotes/AppleScript operators; with no registry match it reaches osascript and can execute attacker-supplied AppleScript/shell commands on the relay host. The relay binds 0.0.0.0 (server.js:58) and register/message targets have no ID validation. Fix: validate clientId/to against one strict base-ID grammar at the server boundary, never embed FOR in AppleScript source (pass it as argv to a fixed script), and add protocol authentication/network restriction appropriate to this host.

2. P1 — PID anchoring is forgeable and permits silent label theft. contestLabel trusts msg.meta.pid; if the newcomer reports the holder's PID, server.js:497-502 returns reseat before checking origin or proving process ownership, then terminates the real holder at :195-201. get_sessions discloses every PID even to an unregistered socket (server.js:402-413). Failure scenario: query sessions, copy CODEX3's PID into a registration for CODEX3, and the server classifies the attacker as a same-process reconnect and evicts the owner—contradicting README:141-151. A client can also pin a label by reporting any unrelated long-lived PID. Fix: a server-minted reconnect capability/nonce bound to the original socket/label, not client-asserted PID; PID can remain diagnostic only.

3. P1 — Delegate mode is an unauthenticated impersonation/read capability, and it can suppress legitimate wakes. server.js:87-109 authorizes delegate=true solely because the TCP peer is loopback; it never proves the server spawned that process or that it is entitled to delegateBase. That socket then reads base-label history (:356-364), sends as the base (:245-268), receives its future direct mail (:249-260), and sets deliveredToDelegate so exec wakes are suppressed (:260, :299-305; notify-hooks.js:95-97). Any local process can impersonate CC6/CODEX3, exfiltrate its seven-day mail, reply as it, and keep the real wake path asleep. Fix: mint a one-time, target/message-bound delegate token in NotifyHooks, pass it only to wake-codex, and require/consume it during delegate registration; reject arbitrary delegate=true.

4. P1 — The 60-second debounce can permanently strand a later message; there is no trailing wake. notify-hooks.js:98-104 records lastFired and simply drops every matching fire in the window; data/notify.json:6 enables 60 seconds. Scenario: M1 wakes a delegate, it reads/replies/exits in 5 seconds; M2 arrives at second 30 after the delegate is gone. deliveredToDelegate is false, but debounce drops the only exec wake. M2 remains unread indefinitely unless a third message arrives after the window. The same happens when runner/spawn fails because lastFired is committed before runner at :104-109. Fix: serialize per target or schedule a trailing-edge wake for the newest suppressed message; clear/retry state on runner error, and use live-delegate/in-flight completion rather than a blind time window.

5. P2 — A rejected same-socket rename destroys the working identity before the contest is decided, and the MCP registry commits the rejected name. server.js:129-141 deletes renamedFrom before checking requestedClientId at :143-169. On rejection the socket remains open with closure-local clientId still equal to the old name, but neither clients map entry exists nor a new identity was granted; it can send as the old label while being invisible/unroutable. Independently, mcp-server.js:916-925 deletes the old registry mapping and writes the new one before any registered acknowledgement; register_rejected at :1116-1131 leaves that false live-PID claim behind. Fix: contest first, atomically swap only on success, and have the MCP commit registry/CLIENT_ID only after registered; roll back on rejection. Add the missing occupied-target rename test.

6. P2 — Wake fallback can resume the wrong Codex conversation when multiple sessions share a cwd. wake-codex.sh:109-127 chooses the newest rollout whose recorded cwd matches whenever exact PID/lsof resolution fails (dead process, lsof denial, stale registry, app-server ambiguity). Two resumable Codex threads in ~/claude-relay are indistinguishable, so mail for CODEX3 can be injected into the other conversation; that wrong thread then receives delegate credentials and may act on CODEX3 mail with unrelated context. README:311-314 calls this exact-session resolution, but cwd is not an exact key. Persist the Codex rollout/session UUID in registry metadata at bridge registration and refuse/notify on ambiguity; do not newest-wins across same-cwd sessions.

7. P2 — Unknown/expired UUID cursors replay old history and can generate stale watcher wakes. MessageStore.filterMessages finds an ID at message-store.js:71-75; if absent and not parseable as a date, :76-80 applies no filter at all. After retention pruning, cache loss, typo, or wrong-target cursor, relay_receive/relay_wait returns the tail of all visible old messages. The watch backfill path server.js:328-347 likewise immediately reports old mail, and RelayWaiter treats every different UUID as after the cursor (relay-waiter.js:56-60). Return an explicit expired/unknown-cursor error or use a cursor carrying ordered timestamp/sequence; never interpret an unknown opaque ID as start-of-history. Add pruning + stale-cursor tests.

8. P2 — Stop-hook rearming can immediately re-wake on the message just processed. relay-stop-hook.sh:93 and relay-watch-loop.sh:44 create SINCE only to whole-second precision, while stored timestamps have milliseconds. If a turn handles mail at 22:39:07.581 and stops at 22:39:07.900, SINCE is 22:39:07Z; MessageStore's strict timestamp comparison (:76-79) sees the already-processed mail as newer, so the newly armed watcher exits immediately and wakes the session again. Use the durable cursor from the processed mail, or at minimum a millisecond-precision timestamp. Also, the per-label lock is check-then-write rather than atomic (relay-stop-hook.sh:83-91), so concurrent Stop hooks can both arm; use mkdir/flock plus trap cleanup.

9. P2 — registry.json updates are atomic per write but not transactional across processes. Every bridge independently reads the whole file, modifies one entry, then renames its private temp over registry.json (mcp-server.js:270-307); clearRegistrySessions does another whole-file replacement at :319-352. Two simultaneous connects/disconnects/renames can both read version N and the later rename erases the other's update. That breaks auto-reclaim, stop-hook ancestry, and wake session resolution. Use a file lock around read-modify-write or per-session files; add a concurrent two-bridge registry test.

10. P3 — A same socket can register as primary and then as delegate without removing its primary map entry. The delegate branch server.js:87-123 bypasses renamedFrom cleanup entirely. On close, the closure-local clientId is the delegate ID, so :432-449 removes only that entry and leaves the base mapped to a closed socket until another claimant overwrites it. Conversely, raw delegate→normal re-registration never clears ws.delegateOf, so history/send authorization remains the old base. Reject mode changes on an already-registered socket, or atomically clean all old mapping and clear delegateOf.
