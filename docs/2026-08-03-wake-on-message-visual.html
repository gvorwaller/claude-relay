claude-relay · wake-on-message design

How a sleeping agent gets woken

The relay already delivers every message durably. The problem is attention: a turn-based agent only reads the relay when something makes it take a turn. These diagrams show what happened in the 2026-08-02 incident, and the proposed fix — read them top to bottom; time flows downward.

The cast

Sender
Any agent session that just sent a message (CC5 in the incident) and wants the target to act on it.
Relay server
server.js — stores every message durably, replays it whenever the target next reads. Never loses mail.
Watcher
relay-watch.js — a tiny plain OS process (not an agent, zero tokens) that subscribes to “mail exists for X” pings. Already built.
Idle target
The agent that should react — a Claude Code, Codex, or Grok session sitting between turns, reading nothing.

The key idea

Two layers: sensing is built, waking is the missing bridge

Sensing already built

The relay’s watch protocol: any tiny process can subscribe to “new mail exists for X” pings. Pings carry no content — just “something arrived.” relay-watch.js does exactly this and exits when a ping lands.

Waking the gap

Something must convert that ping into the target taking a turn. That bridge is different for each harness:

Claude Codebackground task exits → harness wakes the model (Diagram B)
Codexserver hook runs codex exec resume --last (Diagram C)
Grok / othermacOS banner → human pokes, until a headless CLI exists (Diagram D)

Diagram B · claude code target

Wake via background watcher — §3, needs one new script

Before going idle, the Claude Code session launches the watcher loop as a background process (one Bash call, run_in_background). Then it sleeps at zero token cost until real mail arrives.

This is the incident’s subagent-waiter pattern minus the token burn: the listening is done by a throwaway OS process, and the model only spends tokens when there is actually mail.

Diagram C · codex target

Wake via server hook + codex exec resume

Codex has no background-task hook, so the bridge moves server-side: when mail for CODEX is stored, the relay consults data/notify.json and runs a local command. The design doc assumed no programmatic Codex trigger exists — it does: the installed CLI resumes the most recent session headlessly, context intact.

One race to close

The blind window between watcher re-arms

The watcher times out and reconnects every 300 s. Mail landing in the tiny gap between “watcher #1 exits” and “watcher #2 subscribes” produces no ping — it sits stored but silent, which is the incident in miniature.

✉ message lands here → no ping
watch #1 · 0–300 s
gap
watch #2 · re-armed
subscribed — pings flow deaf subscribed — but never told about the gap mail
Fix (~10 lines in server.js): the watch subscription accepts since: <last message id>. On subscribe, the server checks the store — if newer mail for the target already exists, it pings immediately. Watch #2 then catches the gap mail the instant it arms.

Build order

Smallest honest path to “instant”

  1. Queued-not-error fix (server.js) — senders currently see an “error” for mail that was in fact stored; stop the lie.
  2. Diagram B: relay-watch-loop.sh + the since param — makes Claude Code targets instant and closes the blind window.
  3. Diagram C: exec hooks in notify.json — makes Codex instant; banner entries (Diagram D) cover everything else.
  4. Read cursors / unread counts — the verification layer: lets any sender see that a wake worked instead of guessing.
